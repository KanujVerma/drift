# Drift M0 Evidence Kernel Design

## Purpose

Drift M0 is an auditable research evidence kernel. It records structured research objects and immutable audit events so later milestones can evaluate hypotheses without losing failed trials or provenance.

M0 does not connect to brokers, place orders, call language models, backtest strategies, manage portfolios, or execute production code.

## Architecture

The package has four responsibilities:

1. Frozen Pydantic domain models validate hypotheses, dataset references, strategy artifacts, experiment specifications, experiment runs, evidence records, and audit events.
2. Canonical JSON serialization normalizes UTC timestamps, enums, UUIDs, sets, mappings, nulls, and nested Pydantic models before hashing.
3. SHA-256 hashing binds each audit event to its canonical contents and the previous event hash.
4. A SQLite ledger appends events transactionally, rejects update and delete operations with database triggers, retrieves deterministic sequences, replays those sequences, and verifies the complete chain.

SQLite stores research metadata only. A future PostgreSQL adapter must preserve the same event envelope, ordering, uniqueness, immutability, and verification behavior.

## Identity and ordering

Entity and event identifiers are UUIDv7 values generated by Python 3.14. Content hashes are lowercase SHA-256 hexadecimal strings. Version identifiers and deduplication keys remain explicit strings and are never overloaded as entity identifiers.

Ledger order is a database-assigned monotonically increasing sequence number. Timestamps are evidence, not the sole ordering mechanism, because multiple events may share a timestamp and clocks can disagree.

## Event hashing

The genesis event uses 64 lowercase zeroes as `previous_event_hash`.

An event hash is:

```text
sha256(canonical_json(unsigned_event_fields)).hexdigest()
```

The unsigned fields include event ID, type, UTC timestamp, entity type, entity ID, payload, previous hash, deduplication key, and schema version. The event hash does not include itself.

## Trust boundary

Only research-zone foundations exist in M0. No module, setting, environment variable, dependency, URL, or interface provides broker access, order management, market connectivity, or agent orchestration.

Research-generated outputs remain untrusted. A future promotion control plane may consume hashed research artifacts, but research will not receive production credentials or write access to production execution state.

## Retention

Compact provenance remains immutable: hypotheses, experiment specifications and runs, hashes, parameters, metrics, dataset references, evidence lineage, failures, and future promotion history.

Bulky artifacts such as raw datasets, temporary logs, model checkpoints, and duplicated intermediate files may later follow explicit retention rules. M0 records references and hashes but does not expire artifacts.

## Acceptance criteria

- Equivalent logical objects produce identical canonical bytes and hashes.
- Naive datetimes and non-finite floating-point values are rejected.
- Domain models are frozen and reject malformed identifiers, blank required text, invalid time ranges, illegal self-references, and inconsistent experiment run state.
- Duplicate event IDs and duplicate deduplication keys are rejected.
- SQLite rejects historical updates and deletes independently of application code.
- Verification detects altered payloads, missing events, reordered sequences, modified previous hashes, and invalid event hashes.
- Replay of the same clean ledger yields identical event output.
- The repository has no broker, MCP, order placement, market API, backtesting, agent, or production credential capability.
