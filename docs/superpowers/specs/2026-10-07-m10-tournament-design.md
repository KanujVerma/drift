## 1. Executive Summary & Problem Statement

Milestone M10 delivers the automated out-of-sample competition harness between incumbent production trading strategies ("Champions") and newly evolved candidate strategies ("Challengers") generated by the recursive R&D loop (M8).

In quantitative finance, strategies that achieve superior in-sample metrics routinely degrade out-of-sample due to data snooping, backtest overfitting, and selection bias across multi-trial explorations. An in-sample winner cannot replace an existing incumbent Champion without demonstrating verifiable, statistically significant outperformance across strictly held-out out-of-sample evaluation data under identical execution and market conditions.

Milestone M10 establishes a rigorous, deterministic head-to-head tournament engine:
1. Paired out-of-sample evaluation across synchronized temporal evaluation windows;
2. Differential risk-adjusted performance attribution (Sharpe, Drawdown, Turnover, Information Coefficient);
3. Statistical hypothesis testing on paired session return series with multiple-testing adjustments;
4. Conservative tenured-champion defense thresholds to prevent churning models on marginal noise;
5. Immutable M0 ledger audit event sealing and queryable historical tournament archives.

---

## 2. Core Invariants & Boundaries

1. **Deterministic Standard Library Math**: All metric calculations, paired differentials, and statistical hypothesis tests use Python standard library (`decimal.Decimal`, `math`, `statistics.NormalDist`). Zero third-party numeric libraries (`numpy`, `scipy`) in production core.
2. **Strictly Non-Promotable Exploratory Boundary**: Exploratory evaluation evidence (e.g., generated using free Alpaca Basic or synthetic feeds) is strictly non-promotable. A tournament run using exploratory evidence produces exploratory ranking only; promotion to live or canary trading requires an independent run against promotion-qualified M1e data.
3. **Execution Separation**: Zero broker connection, order placement, or capital allocation authority. M10 only outputs deterministic promotion or rejection verdicts and records them to the M0 ledger.
4. **Complete PnL Integrity**: Per Issue #152 and M5 standards, tournament evaluation requires complete realized PnL evidence (`RealizedPnLCompletenessV1.is_complete == True`). Incomplete basis disposals disqualify a match.
5. **Zero Unicode Em Dashes**: The Unicode em dash (U+2014) is strictly forbidden across all code, docstrings, comments, commit messages, and markdown files. ASCII hyphen (-) is used exclusively.
6. **Immutable Ledger Sealing**: Every match outcome is sealed into the SQLite ledger with schema versioning, SHA-256 content hashes, and deduplication keys.

## 3. Head-to-Head Tournament Protocols

### 3.1. Paired Evaluation Execution

For any tournament match:
- Both Champion and Challenger are evaluated across the exact same evaluation window $[T_{\text{start}}, T_{\text{end}}]$, universe of assets, and rebalance dates.
- Both receive identical historical input data up to $T_{\text{start}}$ for warm-up initialization.
- Simulation yields paired session return vectors:
  $$r^{\text{champ}} = (r_1^C, r_2^C, \dots, r_N^C), \quad r^{\text{chall}} = (r_1^H, r_2^H, \dots, r_N^H)$$
  and session excess return difference vector:
  $$\Delta r = r^{\text{chall}} - r^{\text{champ}} = (\Delta r_1, \Delta r_2, \dots, \Delta r_N)$$

### 3.2. Differential Performance Metrics

The tournament engine extracts differential headline metrics:
1. **Annualized Sharpe Differential**:
   $$\Delta \text{Sharpe} = \text{Sharpe}_{\text{challenger}} - \text{Sharpe}_{\text{champion}}$$
2. **Maximum Drawdown Differential**:
   $$\Delta \text{MaxDD} = \text{MaxDD}_{\text{challenger}} - \text{MaxDD}_{\text{champion}}$$
3. **Annualized Turnover Ratio**:
   $$\text{TurnoverRatio} = \frac{\text{Turnover}_{\text{challenger}}}{\max(\text{Turnover}_{\text{champion}}, 1.0)}$$
4. **Information Coefficient (IC) Differential**:
   $$\Delta \text{IC} = \text{IC}_{\text{challenger}} - \text{IC}_{\text{champion}}$$

### 3.3. Statistical Superiority Test

To verify that outperformance is not a lucky draw from noise:
1. Compute mean paired session differential $\bar{\Delta r}$ and sample standard error:
   $$SE(\Delta r) = \sqrt{\frac{1}{N(N-1)} \sum_{i=1}^N (\Delta r_i - \bar{\Delta r})^2}$$
2. Compute paired test statistic:
   $$t_{\text{paired}} = \frac{\bar{\Delta r}}{SE(\Delta r)}$$
3. Compute two-sided p-value $p$ via asymptotic normal CDF (`statistics.NormalDist`).
4. Apply multiple-testing adjustment based on the total number of challengers evaluated in the research campaign ($K$ trials from M6 memory archive), adjusting the effective significance threshold $\alpha_{\text{adjusted}} = \frac{\alpha}{K}$ (Bonferroni) or Deflated Sharpe Ratio.

### 3.4. Decision Verdict Gatekeeping

The tournament issues one of the following deterministic verdicts:

| Verdict | Meaning | Condition |
| :--- | :--- | :--- |
| `PROMOTED` | Challenger dethrones Champion | $\Delta \text{Sharpe} \ge \Delta_{\min}$, $p \le \alpha_{\text{adjusted}}$, $\text{MaxDD}_{\text{chall}} \le \text{MaxDD}_{\text{champ}} \cdot (1 + \text{slack})$, $\text{TurnoverRatio} \le \tau_{\max}$ |
| `REJECTED_INSUFFICIENT_OUTPERFORMANCE` | Outperformance is below required hurdle | $\Delta \text{Sharpe} < \Delta_{\min}$ |
| `REJECTED_STATISTICALLY_INSIGNIFICANT` | Difference is statistically indistinguishable from noise | $p > \alpha_{\text{adjusted}}$ |
| `REJECTED_EXCESSIVE_DRAWDOWN` | Challenger suffers excessive tail risk | $\text{MaxDD}_{\text{chall}} > \text{MaxDD}_{\text{champ}} \cdot (1 + \text{slack})$ |
| `REJECTED_EXCESSIVE_TURNOVER` | Challenger churns portfolio excessively | $\text{TurnoverRatio} > \tau_{\max}$ |
| `REJECTED_INCOMPLETE_EVIDENCE` | Realized PnL completeness violated | `is_complete == False` |

## 4. Domain Models & Ledger Schemas

Defined in `src/drift/domain/tournament.py`:

```python
class TournamentDecision(StrEnum):
    PROMOTED = "promoted"
    REJECTED_INSUFFICIENT_OUTPERFORMANCE = "rejected_insufficient_outperformance"
    REJECTED_STATISTICALLY_INSIGNIFICANT = "rejected_statistically_insignificant"
    REJECTED_EXCESSIVE_DRAWDOWN = "rejected_excessive_drawdown"
    REJECTED_EXCESSIVE_TURNOVER = "rejected_excessive_turnover"
    REJECTED_INCOMPLETE_EVIDENCE = "rejected_incomplete_evidence"


class TournamentParticipantV1(FrozenModel):
    participant_id: UUID7
    strategy_type: NonBlankStr
    parameters: dict[str, Any]
    parameters_hash: SHA256Hash
    trial_id: UUID7 | None = None
    is_incumbent_champion: bool = False


class TournamentConfigV1(FrozenModel):
    tournament_id: UUID7
    min_delta_sharpe: Decimal = Decimal("0.20")
    significance_alpha: Decimal = Decimal("0.05")
    max_drawdown_slack: Decimal = Decimal("0.10")  # max 10% worse drawdown
    max_turnover_ratio: Decimal = Decimal("2.50")  # max 2.5x champion turnover
    min_evaluation_sessions: int = Field(default=60, ge=10)
    created_at: UTCDateTime
    config_hash: SHA256Hash


class TournamentMatchRecordV1(FrozenModel):
    match_id: UUID7
    tournament_id: UUID7
    champion: TournamentParticipantV1
    challenger: TournamentParticipantV1
    champion_sharpe: Decimal
    challenger_sharpe: Decimal
    delta_sharpe: Decimal
    champion_max_drawdown: Decimal
    challenger_max_drawdown: Decimal
    turnover_ratio: Decimal
    paired_t_stat: Decimal
    p_value: Decimal
    decision: TournamentDecision
    rejection_reasons: tuple[str, ...] = ()
    evaluated_sessions_count: int
    started_at: UTCDateTime
    completed_at: UTCDateTime
    record_hash: SHA256Hash
```

## 5. Ledger Audit Event Payloads

1. `m10.match.completed`: Sealed upon completion of a head-to-head match containing `TournamentMatchRecordV1`.
2. `m10.champion.promoted`: Sealed when a Challenger successfully dethrones the Champion.
3. `m10.challenger.rejected`: Sealed when a Challenger fails to satisfy promotion criteria.

## 6. Implementation Slice Plan

1. **M10-1: Domain Models, Schemas, and Audit Payloads**:
   - `src/drift/domain/tournament.py`: `TournamentDecision`, `TournamentParticipantV1`, `TournamentConfigV1`, `TournamentMatchRecordV1`, hash helpers, audit payloads.
   - Unit tests in `tests/unit/test_tournament_domain.py`.

2. **M10-2: Statistical Differential Comparator**:
   - `src/drift/tournament/comparator.py`: Paired returns comparison, t-stat, p-value calculation, multiple-testing correction, gatekeeper evaluation.
   - Unit tests in `tests/unit/test_tournament_comparator.py`.

3. **M10-3: Head-to-Head Tournament Runner**:
   - `src/drift/tournament/runner.py`: `TournamentRunner`. Orchestrates paired evaluation, extracts metrics, applies comparator, produces match record.
   - Unit tests in `tests/unit/test_tournament_runner.py`.

4. **M10-4: M0 Ledger Sealing and Historical Tournament Archive**:
   - `src/drift/tournament/recorder.py`: `TournamentRecorder`.
   - `src/drift/tournament/archive.py`: `TournamentArchive`. Query historical matches, current champion, dethroning lineage.
   - Unit tests in `tests/unit/test_tournament_audit.py`.

5. **M10-5: Adversarial Acceptance Suite and Stress Testing**:
   - `tests/adversarial/test_m10_tournament_adversarial.py`:
     - Marginal noise outperformance rejection;
     - Drawdown and turnover risk breach enforcement;
     - Insufficient session length rejection;
     - Incomplete PnL anti-laundering gatekeeping;
     - Multiple-testing trial count deflation;
     - Cryptographic match record tamper detection.
